# Design notes

Research and design notes for the IB01 firmware. This file is the index.

## Source repos

Citations such as `freedo/docs/PROTOCOL.md:1305` are relative to a working folder that holds these repos side by side:

| Repo | What it is |
| :--- | :--- |
| `freedo/` | Local coordinator for tado V3+ 868 MHz devices: Go daemon, ESP32 + CC1101 radio, Home Assistant integration. |
| `tanoclo/` | Self-hosted Tado backend: REST/WebSocket server, patched Internet Bridge, ESP32 + SX1276 sniffer and emulator. |
| `Tado_Hardware_Teardown/` | Teardown material: logic captures and an over-the-air protocol dissector for Wireshark. |
| `Tado_Hardware_Teardown.wiki/` | Wiki for the teardown: CC110L registers, RF parameters, board analysis, link protocol. |

## Conventions

- One Markdown file per topic, created when the topic comes up and listed in the table below.
- Every factual claim cites its source as a repo-relative path (e.g. `freedo/docs/PROTOCOL.md`), with a line number where useful.
- Mark each claim's status: **verified** (seen on hardware), **documented** (stated in a repo or its docs), or **inferred** (our own reasoning).
- When repos disagree, record the conflict rather than picking one silently.
- Update notes as findings arrive, not at the end of the work.
- Datasheet PDFs, their text extracts (`datasheets/*.pdf`, `datasheets/*.txt`) and firmware dumps are kept locally only and never committed.

## Project decisions

- Crystal offset (owner, 2026-11-20, #11): close #11 as "no per-unit trim needed (one unit)"; `FSCTRL0` stays 0. Instead the radio task warns at run time when the frequency offset has drifted: frames of our own network (good CRC, accepted by the link layer) that average more than 15 kHz `FREQEST` over at least 4 frames give `radio: frequency offset warning: ...; check the crystal (#11)` in the 60 s report, then one "back within limit" line. Only a log line, no automatic trim. Threshold derivation and bench data: `radio-runtime.md`, "Frequency offset warning (#11)". Built and host-tested 2026-11-20; #11 is closed after review and a bench check.
- P7.1, channel 26 with listen-before-transmit (owner, 2026-11-20, #20): #20 (measure delivery with listen-before-transmit) moves to a new stage P7.1 "Channel 26: listen-before-transmit and full check", just before P8 (GitHub milestone created, #20 moved into it). In that stage the channel-26 guard is loosened first (transmit gate, the network's test-channel assertion, and the hard rule in `CLAUDE.md` and `test-bench.md`, which the owner changes at that point), the test network moves to channel 26 next to the live stock network, and one test checks everything there. **Until P7.1 starts, the channel-26 hard rule stays exactly as it is: nothing transmits on channel 26.** Plan: `prototype-plan.md`, "P7.1".
- P7.1 abort rules and run B (owner, 2026-11-21, #20): the draft abort rules of the P7.1 plan (`test-bench.md`, "P7.1 channel 26, plan") are accepted: stop if, against a receive-only baseline, the stock network's ACK share drops more than 15 points, its retransmissions more than double, more than 3 stock frames per 10 minutes are damaged, or the tado app shows trouble. Run B (listen-before-transmit off on channel 26, temporary `RADIO_LBT=0` image) is approved; it suspends rule 8 ("listen-before-transmit stays on", 2026-11-11) for that run only, with its own `fw-reviewer` verdict. The `RADIO_LBT` option is reverted after the test.
- P7.1 run rules (owner, 2026-11-21, #20): (1) **no airtime abort rule:** the 30 s per hour budget stays as it is (`src/airtime.h`), and the plan only notes that the airtime window starts empty at every boot (`radio-runtime.md:165`); (2) **the stock network is checked every 10 minutes** during each transmitting run: the main session reminds the owner at each 10-minute mark, the owner checks the tado app and the devices, and any trouble stops the run at once; `rf-bench` evaluates the SDR captures against the receive-only baseline after each run, per 10-minute block, before the next run starts (near-live decoding optional); (3) **run B is built from its own branch `p71-lbt-off`;** `RADIO_LBT` never goes to main, and the branch is deleted once #20 is measured. Plan: `test-bench.md`, "P7.1 channel 26, plan".
- P7.1 broadcast wake trains on channel 26, and a PAN of our own (owner, 2026-11-21, #20, #43): our network uses PAN `0xABCD`, the same as the stock network (`radio.md`), so the broadcast Router Advertisement's wake train to `ff ff` (`src/csl.c:577-580`, every 200-600 s, `src/link.c:41-47`) wakes every stock CSL device for up to about 1 s, 6-18 times an hour, once we transmit on channel 26. **Accepted for the P7.1 runs only** (`test-bench.md`, "P7.1 channel 26, plan", rule 3). Follow-up **#43**, not part of P7.1, planned after P7.1 and before P8: (1) a test on channel 16 with our spare device re-paired to a network with a PAN other than `0xABCD`; (2) if the device does not work with another PAN, the PAN stays fixed at `0xABCD`; (3) if it works, at the first network formation the bridge draws a random PAN (never `0xABCD`, `0xFFFF` or `0xFFFE`), listens on our channel for traffic with that PAN, draws again if it hears any, and otherwise stores it in the network record's existing PAN field. `open-questions.md` row 33.

- Transmitter on in committed code (owner, 2026-11-17): the committed build transmits on the test channel 16, as the bench images did; `RADIO_TX_ALLOWED` is no longer a `#define` edited by hand in `src/cc110l.h` but a CMake option, default ON, kept as a receive-only build option (`make RADIO_TX_ALLOWED=0`, `cmake -DRADIO_TX_ALLOWED=OFF`). Why: the safety layers are the transmit gate (channel 16 only, at least 999 kHz from channel 26, carrier registers read back, airtime budget, PATABLE cap; `src/txgate.h`, `src/cc110l.c`), the network key (nothing is sent to a device without a network record in flash) and the named pairing target (without `PAIR_TARGET_EUI64` in the gitignored `config/local.cmake` the build holds no code that opens a window or creates a network), not the switch. The bench gates stay: a `fw-reviewer` "safe to flash" verdict before transmit code goes onto the bridge, and the SDR check (`test-bench.md` rule 4; `build.md`, "Build options").
- Self-restart of an unconfirmed update candidate (owner, 2026-11-20, #24): kept. After `FWUPD_TEST_MAX_MS` (10 min, `src/fwupd.h`) without confirmation the application restarts itself; the bootloader rolls back after 3 starts (about 31 min). It also applies when the boot state cannot be read, even for a confirmed image. Rationale: without it a candidate that runs but never gets healthy would run for ever and refuse every new update. Accepted cost: a good image is rolled back if the server stays unreachable for about 30 min after an update (`docs/design.md`, self-update section; `docs/open-questions.md` row 20).
