# Radio runtime behaviour

How to drive the CC110L after init. Source is freedo's working ESP32 + CC1101 firmware: `freedo/firmware/cc1101_bridge/cc1101_bridge.ino` (`.ino` below) and its `README.md`. Validated on air by freedo on a CC1101, not on an IB01.

The stock SPI sequence after init has not been decoded. See `open-questions.md` #1.

Status tags: **[D]** stated in code or docs, **[I]** our own inference.

## Reset and init [D]

1. Manual power-on reset, then `SRES` (`.ino:582-596`).
2. Drive both GDO pins low and read them back to confirm the chip accepted writes (`.ino:599-603`). After reset `IOCFG0` outputs a 135 kHz clock that would flood the interrupt (`.ino:143-146`).
3. Load the register table (`radio.md`), with `FSCTRL1=0x06`, then calibrate and enter RX.

## Receive [D]

- **Interrupts (P2 implementation: GDO0 on both edges, see below):** GDO0 stamps end of frame with a timestamp, GDO2 signals RX FIFO threshold. A periodic tick (8 ms in freedo) also pumps the FIFO, because an overflow raises no interrupt. The FIFO overflows about 11 ms after a frame starts (`README.md:71-77`).
- **Reading the FIFO** (`rxPump`, `.ino:772-816`): read the length byte first, then expect `1 + len + 2` bytes in total. While still receiving, **leave one byte in the FIFO**. Read everything only when the rest of the frame is there.
- **Overflow or bad length:** flush and re-arm.
- **Status bytes:** the last appended byte holds `CRC_OK` in bit 7 (`.ino:700`).
- **`FREQEST`:** freedo reads it when the frame completes, before any strobe or TX (`README.md:49-53`). On the CC110L with `MCSM1 = 3F` that is too late; P2 reads it in the packet (below, #11).
- **Errata:** read `RXBYTES`, `TXBYTES` and `MARCSTATE` until two reads agree (`README.md:99-101`).
- A frame with a bad CRC flushes the FIFO (`README.md:82`).

## Transmit [D]

`ccSendFrame`, `.ino:639-678`.

1. Send `SIDLE`, `SFRX`, `SFTX` in **one** SPI access (`.ino:648-649`). The flush has to happen before TX, because TX ends straight back in RX and the reply arrives about 192 µs later (`README.md:103-108`).
2. Write `[len][payload]` to the FIFO, up to 64 bytes. The radio appends the CRC.
3. Strobe `STX`.
4. For longer frames, top up the FIFO while checking `TXBYTES` for underflow (`.ino:656-675`).
5. Done when `MARCSTATE` has left TX and TX_END and `TXBYTES` is 0. It never shows IDLE, because `MCSM1` returns to RX (`.ino:611-625`).
6. On failure: `SFTX`, then `SIDLE`, `SFRX`, `SRX` (`.ino:575-579,631-635`).

## Answering an uplink [D]

`ccAutoAck`, `.ino:699-725`. Conditions: CRC OK, FCF `69 EC` or `79 EC`, destination is us. It answers **before** decrypting, so no AES is needed in the ACK path.

| Bytes | Content |
| :--- | :--- |
| 0-2 | `42 EE`, seq copied from the frame |
| 3-10 | Sender's 5 address bytes + `C5 1B 00` |
| 11-18 | Coordinator EUI-64 |
| 19-20 | `04 0D`, CSL IE |
| 21-22 | CSL phase, LE |
| 23-24 | `35 0C`, period 3125 |
| 25-26 | `80 3F`, termination IE |
| 27-28 | Inner CRC over bytes 0-26, LE |

Only the phase and CRC vary with time; the rest can be prepared in advance **[I]**.

If the inbound queue is full, send no ACK, so the device retransmits instead of losing data (`README.md:86-88`).

## Sending to a sleeping device [D]

State machine IDLE, RX, WAKE, ACK, FOLLOW (`README.md:63`, `.ino:1402-1473`).

1. **Schedule** on the device's next sample, using its stored anchor.
2. **Wake train:** repeat `25 <seq> CD AB <dst short> 82 0E <rendez LE> 80 3F` (`.ino:1357-1358`). `seq` is the seq of the Data frame that follows. `rendez` is time remaining in 320 µs units (`freedo/tado/mac.go:24`). Broadcast uses dst `FF FF`.
3. **End** on a wake frame with `rendez` 0, then send the Data frame immediately (`.ino:1366-1373`).
4. **ACK window:** check seq and addresses, then refresh the anchor from the ACK's GDO0 timestamp. Send no ACKs of our own in this window, because that would cover the target's ACK (`README.md:110-117`).
5. **Follow window:** optional, for a reply straight after the ACK.

The wiki says the wake seq increments per frame (`wiki/Tado-868-MHz-Link-Protocol.md:267`). Follow freedo, which matches its captures (`freedo/docs/PROTOCOL.md:1433`).

## Anchors [D]

`README.md:137-156`.

- Sampling period nominally 1 s.
- Guard starts at 40 ms each side of the sample and grows by 30 ppm of time since the last refresh, up to half a period.
- Short train about 79 ms when the anchor is fresh; full 1 s train when it is not known.
- 4 missed ACKs in a row drop the anchor.
- Use the GDO0 stamp only if it is later than the Data frame.
- No drift measurement is needed; device clocks measured -6 to +18 ppm.

## Listen before transmit [D]

The commercial bridge uses a random backoff of 0-6 × 640 µs and a 3.97 ms listen before the first frame of a job. Freedo leaves it out, because adding it cut answered jobs from 81.7% to 43.9%, cause unknown (`README.md:125-135`). **Decision (user, 2026-11-11): implement it as stock does**, then measure delivery on the prototype against freedo's finding.

## Porting to the F411 [I]

- Freedo splits radio and serial across two ESP32 cores. The F411 has one core, so radio work belongs in interrupts or a high-priority task.
- Radio and flash share SPI1. Flash access must never run during a train, ACK window or ACK transmission. **As built (#22, 2026-11-18) [I]:** flash work starts only at a quiet moment of the radio task (no frame arriving, no coordinator transaction, so no train; verified on air 2026-11-18 with 71 erases forced while a short train waited, all delivered at attempt 1 **[V]**, `test-bench.md`, "Flash work during traffic (#22) rerun"); no flash bus transaction starts while a frame arrives or a frame of ours (an ACK) is on the air; during a program or erase cycle the radio task keeps pumping the FIFO and preparing ACKs (`design.md`, "Implementation: flash work during radio traffic (#22)"). The update's flash work (#24, 2026-11-19, not flashed) runs the same way, one bounded operation at a time (at most one 4 KB sector erase with its blank check, about 250 ms), posted by the low-priority update task (`design.md`, "Implementation: self-update, application side (#24)").
- Freedo's host-to-radio split goes away: the ring, queue and CCM all run on the F411.

The sample attaches to the next completed frame; it is dropped (counted "stale sample dropped") if more than 2 GDO0 edges passed since it was taken (its own end plus the next sync), and cleared on flush, re-init and the next sync. The sampled RSSI is cross-checked against the appended RSSI byte (counted only).

**Channel.** `RADIO_RX_CHANNEL` = 26 (868.3237 MHz), the stock network's channel, so frames from real devices arrive; receive-only there is allowed (`test-bench.md` rule 3). `RADIO_PROTECTED_CHANNEL` = 26 is defined now for the P5 transmit guard. `_Static_assert`s recompute base 863.125 MHz, spacing 199.951 kHz, channels 10 and 26, IF, data rate, bandwidth and deviation from the table with the datasheet formulas (`datasheets/cc110l.txt:3700-3711,3724-3736,3755-3778,3869-3906`).

**Register table.** The stock burst write `0x00..0x2E` (`radio.md`, "Stock CC110L register table"), as one 47-byte burst, with four changes:

| Reg | Stock | P2 | Why |
| :-- | :-- | :-- | :-- |
| `IOCFG2` | `04` RX overflow | `00` RX FIFO at or above threshold | Wake for long frames, as freedo (`freedo/cc1101/cc1101.go:47`) |
| `IOCFG0` | `01` threshold or end of packet | `06` sync word until end of packet | Rising edge = sync (FREQEST/RSSI sample), falling edge = end of every packet, CRC good or bad; also falls on RX FIFO overflow and length-filtered packets (`cc110l.txt:2916-2918`) |
| `CHANNR` | `00`, later `1A` | `1A` (`RADIO_RX_CHANNEL`) | |
| `FSCTRL1` | `18` | `06` | Owner decision (`radio.md`, Conflicts) |

`FIFOTHR = 03` keeps the stock 16-byte RX threshold, which leaves 48 bytes, about 7.7 ms at 160 µs per byte, before an overflow. `MCSM1 = 3F`: RXOFF_MODE and TXOFF_MODE both RX (`cc110l.txt:3929-3955`). `MCSM0 = 08`: no automatic calibration, so the firmware strobes `SCAL` once after loading the table and checks `FSCAL1 != 0x3F` for PLL lock (`cc110l.txt:2756-2759`). The table is read back after the burst and compared, except the four "Not used" addresses; any mismatch keeps the radio in IDLE and retries in 10 s.

`freedo` and `cc110l-vs-cc1101.md` prefer `IOCFG0 = 07` (CRC-OK packet) for the CSL end-of-frame timestamp. P2 uses `06` instead, so CRC failures are seen and counted; `06` also gives the end-of-frame edge for P5. Revisit in P5.

**Receive flow.** Interrupts only wake the radio task (`design.md`). The task blocks on a notification with a timeout (2 ms while a frame is being assembled, else 100 ms), so its watchdog check-in never stops. The pump follows freedo's `rxPump` (above): stable `RXBYTES` reads, length byte first, one byte left in the FIFO until the packet is complete (`cc110l.txt:2593-2597`), `FREQEST` and RSSI sampled in the packet right after sync (after the FIFO pump), not after it (#11). Overflow, a length of 0 or above `PKTLEN = 0x80`, or a frame stuck for 60 ms: `SIDLE`, wait for IDLE, `SFRX`, `SRX` (`cc110l.txt:1449-1451,1501`). **Deviation from freedo:** a bad CRC does not flush the FIFO. The chip still wrote exactly `1 + len + 2` bytes, so the FIFO stays aligned, and a flush would need `SIDLE`, which would cut a following packet that may already be arriving.

**Status bytes.** RSSI from the first appended byte, `RSSI_dBm = signed/2 - 74` at 868 MHz (`cc110l.txt:2130-2144`). `CRC_OK` is bit 7 of the second; bits 6:0 are reserved on the CC110L, where a CC1101 has LQI (`cc110l.txt:1747-1757`). The log prints those bits as `lqi(rsvd)` to see whether this die fills them. **[V]** (2026-11-12) they are filled: 43-48 on CRC-OK frames, so this die appears to fill an LQI-like value. `FREQEST` is printed raw and in Hz, at `26 MHz / 2^14 = 1586.9 Hz` per unit (`cc110l.txt:4429-4434`).

**Log.** One line per frame with tick time, length, CRC, RSSI, `lqi(rsvd)`, in-packet `FREQEST` and the first three MAC bytes (frame control and sequence number) only; no addresses or payload. Wake-up frames (frame type 5) are summarised per train (count, CRC OK, RSSI range, in-packet count, mean in tenths of Hz, min..max `FREQEST`). Every 60 s: `radio: 60 s: freqest in packet N, none N (stale sample dropped N), sync rssi differs N` (since #11, 2026-11-20, followed by `; our network N frames, mean +H Hz (min..max)`, "Frequency offset warning (#11)" below); frames, CRC OK and bad, wake frames, overflows, bad lengths, stale frames, re-arms, re-inits, SPI errors, and the flash ID checks. The cloud LED toggled on each CRC-OK frame (P2 test wiring); since P4 (#15) it shows the server session instead.

**Health check every 10 s.** `IOCFG0` must still read `06`; otherwise the radio lost its configuration (brown-out or reset) and is re-initialised. `MARCSTATE` IDLE is re-armed.

**Transmit guard (receive-only image).** In P2 `RADIO_TX_ALLOWED` was 0 and `#error`ed if set. Since 2026-11-17 it is a build option, default 1 (owner decision, `README.md`, "Project decisions"; `build.md`, "Build options"); a receive-only build (`make RADIO_TX_ALLOWED=0`) keeps this guard exactly, and in a transmitting build it stays the guard outside the transmit functions ("P5 link implementation (#17)" below). Every SPI header byte goes through one check in `src/cc110l.c`:
- Strobes: only `SRES`, `SCAL`, `SRX`, `SIDLE`, `SFRX`, `SNOP`. `STX`, `SFSTXON` (and `SXOFF`, `SPWD`, `SFTX`) call `fw_panic`. The check covers strobe headers with either R/W bit, since both execute the strobe (`cc110l.txt:1453-1456`). `cc110l_strobe()` is the only strobe function.
- No TX FIFO or `PATABLE` access, and no write outside `0x00-0x2E`, including a burst that would run past `0x2E`.
- Any write of `MCSM1` with RXOFF_MODE or TXOFF_MODE set to FSTXON or TX (`cc110l.txt:3929-3955`), and any `PKTCTRL0` other than FIFO mode with variable length (since 2026-11-17 also refused: fixed, infinite and the reserved length mode, `datasheets/cc110l.txt:3673-3684`), is refused.
- Every chip status byte is checked for STATE TX or FSTXON (`cc110l.txt:1381-1405`); the radio task confirms with `MARCSTATE` and, if the chip really is in a TX state, strobes `SIDLE` and stops the board (`fw_panic`, watchdog reset). The 10 s health check does the same.
The CC110L has no automatic acknowledgement and no wake-on-radio (`datasheets/cc110l-vs-cc1101.md`), so with `STX`, `SFSTXON` and the MCSM1 TX paths refused it has no way to transmit.

**Reset.** CSn low 10 µs, high 50 µs, then `SRES` with `CHIP_RDYn` (SO low) awaited before and after, bounded at 5 ms (`cc110l.txt:2398-2407`). SCLK idles low during this, where the datasheet's power-up sequence sets it high; the chip is already past its automatic power-on reset and `SRES` resets it fully either way [I], as in freedo (`.ino:582-596`). The GDO interrupts stay off from reset until the table is loaded, because `IOCFG0`'s reset value outputs a 135 kHz clock (`cc110l.txt:2894-2896`). `PARTNUM`/`VERSION` are logged; the datasheet gives `00`/`17`, the version "subject to change" (`cc110l.txt:4419-4426`).

## P5 link implementation (#17) [I]

Host-tested, built; the TX-off image was reviewed (`fw-reviewer`, "safe to flash"), flashed and verified (2026-11-17); the first test frames went out with a temporary sender, since reverted (`test-bench.md`, "First transmit test" [V]). Until 2026-11-17 the committed image could not transmit (`RADIO_TX_ALLOWED` 0, edited to 1 only in local bench images). Since the owner decision of 2026-11-17 the transmitter is built in by default: `RADIO_TX_ALLOWED` is a CMake option, default ON, and `make RADIO_TX_ALLOWED=0` builds a receive-only image (`cmake/CMakeLists.txt:25-43`, `src/cc110l.h:21-38`, `build.md`, "Build options"); the boot log's first line names the variant. What a transmitting image may send is bounded by the transmit gate, the airtime budget and the PATABLE cap (below), by the network key and by the named pairing target. Without a network key nothing is queued for the air and no ACK is prepared (`src/radio_rx.c:419`, `link_ready()` in `src/link.c:121`). Since #37 the key is set at boot from a valid network record in flash (`design.md`, "Implementation: network and counter records (#37)"); no network is created until the owner opens the first pairing window (#19, "Pairing (#19)" below), which needs a target named at build time, so on the bench there is still no key, and a build without a target has no code that creates one.

**Modules.** Hardware-independent and tested on the host: `src/mac.c`, `src/ccm.c`, `src/lowpan.c`, `src/txgate.c`, `src/csl.c`, `src/relay.c`, `src/msgq.c`, `src/link.c`. Hardware side: `src/radio.c` (task loop), `src/radio_rx.c` (interrupts, receive), `src/radio_csl.c` (the coordinator's `csl_port_*` functions), `src/radio_pair.c`, `src/radio_bringup.c` and `src/radio_flash.c` and `src/cc110l.c` (the only code that can key the transmitter). **Enhanced ACK path.** Differs from the plan in `radio.md`, "ACK prebuild", in two points: the ACK bytes go into the TX FIFO in the interrupt, not during reception, and `STX` is strobed from IDLE, not from RX. From RX, `STX` only works if the channel is clear (`MCSM1` CCA_MODE 3, `datasheets/cc110l.txt:2253-2262`), which right after a packet it may not be; from IDLE no assessment applies.

1. Task, while the Data frame arrives: once its 16 header bytes are out of the FIFO, `ack_consider()` (`src/radio_rx.c:416`) builds the ACK. Conditions: identity and key set, the frame is a unicast Data frame addressed to our EUI-64, the coordinator is not in a train or ACK window, the uplink queue has room for the largest message, the chip's frequency registers read back as written, the GDO interrupts are on.
2. Hand-over, with the GDO interrupts masked: `cc110l_ack_prepare()` runs the transmit gate (`src/txgate.c`) on the ACK and the header it answers, and arms it only if no GDO0 edge has come since the frame was seen arriving and GDO0 is still high. So the next CRC-OK edge is that frame's.
3. Interrupt on the CRC-OK edge (`exti1_isr`, `cc110l_ack_fire_from_isr()`): `SIDLE`, `SFTX`, the 30 bytes, then `STX` in a second access. A new sync edge or the end of frame handling drops an ACK that was not sent.

Latency, estimate only, nothing measured yet: interrupt entry a few µs; about 36 bytes at 6 MHz, 60-80 µs to the `STX`; IDLE to TX 75 µs (`datasheets/cc110l.txt`, Table 5-11). The preamble should start **0.15-0.3 ms** after the CRC-OK edge, against the 0-1 ms target and the 0.35-0.39 ms of stock devices (`test-bench.md`). The interrupt can be held off by one SPI1 access of the radio task, at most a 64-byte FIFO read, about 0.1 ms; the net task's P-256 steps do not mask it. To be measured with `tools/sdr/demod.py` (#18).

**Transmit guard, from the bottom up.** Rules in `src/txgate.h`.

- `guard_header()` in `src/cc110l.c` refuses `STX`, `SFTX` and the TX FIFO except inside the transmit functions, and `SFSTXON`, `SXOFF`, `SPWD` and the `MCSM1`/`PKTCTRL0` values that transmit by themselves always (as in P2).
- **Output power.** `PATABLE` is written only by `cc110l_set_pa()`, one byte to `PATABLE[0]`, never a burst (`PATABLE[1]`), and `FREND0` must keep `PA_POWER = 0` (`datasheets/cc110l.txt:2799-2805`). It accepts only the reset value `0xC6` (9.6 dBm wire-wound, 8.5 dBm multi-layer inductors, `cc110l.txt:2834-2839,2868-2873`) and the 868 MHz settings documented at 0 dBm and below (`cc110l.txt:2816-2832,2852-2865`), read back after the write. The PA code is not monotonic: `0xC0`-`0xC5` are numerically below `0xC6` but give 10-12 dBm, so a numeric "at most 0xC6" would let them through; the check is a list. Output level `RADIO_PA_LEVEL = 0x26` (set at every bring-up), -10 dBm with wire-wound inductors (`cc110l.txt:2828`; -10 dBm is `0x27` with multi-layer ones, `:2862`; the IB01's variant is not known). Stock keeps `0xC6` (`radio.md:53`). Nothing is sent until the setting has read back since the last reset, and it is read back again before every frame and ACK and in every health check. The receive-only image now writes `PATABLE` too (a lower power, no transmission).
- `STX` is strobed in two places only: `cc110l_tx_start()` (task) and `cc110l_ack_fire_from_isr()` (interrupt). Both need `RADIO_TX_ALLOWED`, a full register table written since the last reset, and the gate's verdict on the carrier those registers give: at least 999 kHz from channel 26, on the channel plan, the image's network channel only: `RADIO_NET_CHANNEL`, default 16 (10 until 2026-11-17; `build.md`, "Build options"). Only in a channel-26 build with the opt-in `RADIO_ALLOW_CH26=1` (stage P7.1, #20) does the gate pass channel 26's own carrier, never a neighbour's, and in that build it also refuses unicast to any device but the build's pairing target (`src/txgate.h` rules 1 and 6).
- The chip's own frequency registers are read back and compared before every frame the task sends, and before every ACK is prepared; the interrupt refuses an ACK whose read-back is older than 50 ms. A chip that reset holds 800 MHz, not the table.
- Frame rules: an Enhanced ACK only as the byte-for-byte answer to a unicast Data frame addressed to our EUI-64; other frames only with our source address and of a class a coordinator sends; a beacon only flagged as pairing, on the test channel, as the answer to a Beacon Request.
- One transmission at a time: a new frame is refused while one of ours is on the air, and the interrupt sends no ACK then.
- **Airtime (duty cycle).** The test channel 16 (866.3242 MHz), like channel 10 before it, lies in the 865-868 MHz band: 25 mW e.r.p., at most 1 % duty cycle (36 s per hour) **[I]**: ERC Recommendation 70-03, Annex 1, band h1.4, recalled, not checked against a copy in this repository; our listen-before-transmit is not the regulated LBT+AFA alternative. `src/airtime.c` keeps a rolling window of 61 one-minute buckets (at least the last 60 minutes) with a budget of **30 s per hour**. The driver charges every frame before it is keyed: `cc110l_tx_start()` (wake-up and Data frames, Router Advertisements, everything the coordinator sends) and `cc110l_ack_prepare()` (an Enhanced ACK, charged when prepared, so the interrupt never touches the budget). A frame that does not fit is refused (`CC_TX_DUTY`), never queued; the coordinator fails that attempt and drops the datagram after its 3 attempts. Charge per frame: (11 + length) × 161 µs + 100 µs, above the real 160.04 µs per byte plus 75.2 µs IDLE to TX. The PHY values (crystal, channel plan, bit rate, bytes around a frame, byte time, IDLE to TX) have one home, `src/phy.h` (#34), which also says why this charge rounds up while the driver's TX watch window uses the nominal 160 µs and 75 µs plus a 2 ms margin. Logged every minute: airtime of the last hour, frames and ACKs refused for airtime. **Reset (owner decision, 2026-11-17):** the window starts empty at every boot; no record is kept over a reset, and this is not a use case to cover. A reset loop that transmits after each boot could therefore exceed the limit.
- The radio code (`src/radio_rx.c`, `src/radio_csl.c`, `src/radio_pair.c`) sends nothing while the GDO interrupts are off (storm guard or failed bring-up), and the TX-state watch of P2 now stops the board only for a TX state outside the airtime of a frame we started.

**Host tests of the driver.** `tests/host/test_cc110l.c` compiles `src/cc110l.c` with the switch set for that one translation unit and runs it against a simulated chip (`tests/host/cc110l_model.h`) that logs every `STX` with the carrier its own registers give. `tests/host/test_cc110l_off.c` runs the driver as built. `make test`: 1475660 checks in 9 programs (with `tests/host/test_airtime.c`), 0 failed (2026-11-17, after the review fixes) **[V]** on the host.

**Open, for the review and the bench.**

- **Status bytes against the early `SIDLE` [I].** The interrupt strobes `SIDLE` some 10-20 µs after the CRC-OK edge. If the chip appends the two status bytes later than that, the frame never completes in the FIFO and is dropped as stale after 60 ms although it was acknowledged. The datasheet does not say. On the bench: `stale` must stay 0 in the minute log while `acks sent` counts.
- **`GDO2` after a flush [I].** `IOCFG2 = 07` de-asserts "when the first byte is read from the RX FIFO" (`datasheets/cc110l.txt:2919`). Whether `SFRX` also de-asserts it is not stated; if not, the first good frame after a flush gets no ACK, and the device repeats it.
- **Listen before transmit: sync words and RSSI (after the first review).** Busy if a GDO0 edge comes during the 3.968 ms listen, or the RSSI is at or above -85 dBm at its start, at its end, or at the radio task's loop pass in between (about one) **[I]**. The RSSI register updates continuously in RX until a sync word freezes it (`datasheets/cc110l.txt:2113-2115`). The threshold is about 19 dB above the sensitivity at 868 MHz, 38.4 kBaud (-104 dBm, `cc110l.txt:600-603`) and below the -41 to -72 dBm of the frames seen in P2; the minute log prints the listens found busy by RSSI and the highest RSSI of the minute's listens, to set it from bench data. What the stock coordinator listens for is not known (#20).
- **Calibration and PLL lock (#11, after the first review).** `MCSM0 = 08` stays (no automatic calibration: it would add 0.8 ms to IDLE to TX, `datasheets/cc110l.txt` Table 5-11, which an Enhanced ACK cannot wait for). `cc110l_calibrate()` in `src/cc110l.c` is the only path that grants the lock: from IDLE, up to 3 × `SCAL`, wait for IDLE, `FSCAL1 != 0x3F` (`cc110l.txt:2756-2761`), then the carrier registers are read back; the radio task then compares registers `0x00-0x18` as the health check does. Three tries without lock latch the transmitter off until the next reset of the chip (the next bring-up); the receiver keeps running. Every `SCAL` strobe, configuration write and reset clears the lock. Policy **[I]**: the datasheet asks for calibration "regularly" with no interval (`cc110l.txt:2740-2752`), so the task recalibrates every 5 minutes at a quiet moment (`RECAL_PERIOD_MS` in `src/radio.c`, about 1 ms deaf receiver), and a calibration older than 12 minutes (`CC_CAL_MAX_AGE_US`) stops the transmitter. Whether 5 minutes is needed, or enough, is to be seen on the bench: `FSCAL3-1` are logged at every calibration.
- **Radio task stack:** 896 words (3584 B; 640 before the #19 review, `src/app.c:25-36`). Deepest path by `-fstack-usage` (build without LTO, 2026-11-17) **[I]**: the pair button on a bridge without a network, `radio_task_run` (232 B with the transmitter built in, the trigger inlined; 240 B since the 10-minute window's LED and exchange log, 2026-11-17) → `network_create` (88) → `rng_random` (24) → `mbedtls_ctr_drbg_random` and `_with_add` (104) → a reseed, if one is due (`mbedtls_ctr_drbg_reseed_internal` 416, `block_cipher_df` 832) → AES (124): about 1.8 KB, plus up to 104 B of exception frame with the FPU, so about 1.9 KB. The receive and coordinator paths (a log line from the coordinator) are about 1.0-1.2 KB. The reseed was not moved out of the radio task: `network_create()` allows one attempt per boot, so a draw that fails because a reseed is due (or the net task holds the DRBG) would block network creation until the next boot; the larger stack is the simpler fix. Heap cost: the stacks come from the FreeRTOS heap, so the lowest free heap measured with 640 words (8976 B, `test-bench.md:160`) drops by 1024 B to about 7.9 KB **[I]**; static RAM is unchanged. Measure on the bench: the `alive:` line's unused radio words after a window was opened on a bridge without a network record.
- **ACK interrupt failures (after the first review).** If the second access (the `STX`) cannot be opened after the first access made the chip IDLE, the interrupt opens a third: `SIDLE`, `SFTX`, `SRX`, keeping the RX FIFO, and has the radio task confirm RX with `MARCSTATE` (a status byte cannot, since IDLE is also reported for transitional states, `datasheets/cc110l.txt:1381-1385`). If that access fails too, or the chip is not in RX, the task aborts and re-arms at once (`cc110l_tx_abort()`, then `SIDLE`, `SFRX`, `SRX`), and re-initialises if that fails; the frame is dropped and its device repeats it. Counted as "acks failed" and "re-armed" in the minute log. A status byte that wrongly shows a transmit state at the `SIDLE` costs only that ACK: the interrupt strobes `SRX` and the frame is still taken.
- **Own-frame window (fixed after the first review).** `cc110l_tx_expected()` compared an end time as a signed difference and cleared its flag only when called; in a quiet network nothing calls it after the last ACK, and from 35.8 to 71.6 minutes later it read "on the air" again, so the TX-state watch would have taken a stray TX state for ours. It now keeps start and length and compares an unsigned elapsed time; the task calls it every loop pass; and the task clears the flag only while no ACK is prepared, so the interrupt cannot set it between the task's check and its store.

## Frequency offset warning (#11)

**Decision (owner, 2026-11-20):** no per-unit trim (one unit; `FSCTRL0` stays `0x00`), and a run-time warning when the frequency offset of our network's frames has drifted too far. It only logs: no trim, no `FSCTRL0` write, nothing changes in what or when the bridge sends. Built 2026-11-20 (`src/freqoff.c`, `src/freqoff.h`), host-tested (`tests/host/test_freqoff.c`), not on the bench yet.

**What is counted [I].** The in-packet `FREQEST` sample ("P2 receive-only implementation (#9)" above) of a frame with a good CRC that the link layer accepted from our own network, `link_rx_from_network()` (`src/link.c`): a frame opened under the network key (Data to our address: to server, fragment held, duplicate, not relayed, dropped for a full queue, the pairing target's 2.04 to `d/pair`; broadcasts), or the Enhanced ACK that closed our own transaction (sequence number, both addresses and FCS checked, `mac_ack_answers()` in `src/mac.c`). Not counted: bad CRC, other devices' ACKs, Data for other addresses, frames without a key, MIC failures, beacon requests (answered or not), frames under the pairing key, wake-ups and anything else, and frames without an in-packet sample.

**Hook point.** `frame_done()` in `src/radio_rx.c:465`, in the radio task, after `link_on_frame()` has classified the frame and after `beacon_answer()`. By then the Enhanced ACK has gone from the CRC-OK interrupt (budget 0-1 ms, measured 226 us median, `test-bench.md`, "ACK timing (#18)"), and the beacon has been sent or dropped (2.4-7.4 ms, "Beacon answer timing" below). The added work is a few additions in the task; the report and the log lines run in `log_minute()`, which runs only while no packet arrives and no transaction holds the air. Nothing is added to an interrupt.

**Report.** The 60 s line `radio: 60 s: freqest in packet ...` ends with `; our network N frames, mean +H Hz (min..max)`: this minute's counted frames, their mean in Hz and the range in `FREQEST` units. A separate verdict window holds the frames since the last verdict. At each report a window with at least 4 frames (`FREQOFF_MIN_FRAMES`) is judged and starts again; a smaller one is carried into the next minute, because one device gives only a few frames a minute (below). Crystal drift is slow, so a window spread over several minutes is still one reading [I].

**Warning.** When |mean| of a judged window is above 15 kHz (`FREQOFF_LIMIT_HZ`), compared exactly in integers:

`radio: frequency offset warning: devices average +16.2 kHz from us over 12 frames (limit 15.0 kHz); check the crystal (#11)`

It comes again in every report whose window is still above the limit, so at most once a minute. The first judged window at or below the limit after a warning gives one `radio: frequency offset back within limit: devices average +3.2 kHz from us over 6 frames (limit 15.0 kHz)`. There is no hysteresis, so a mean right at the limit may alternate between the two lines, at most one a minute. The mean mixes every device heard. A shift of the bridge's own crystal moves all of them alike, and that is what the warning watches. A single device that is far off among several shows first in the minute line's min..max.

**Sign [I].** A positive `FREQEST` means the sender's carrier is above ours. On channel 16 the spare device read +1 to +3 units (below) while the SDR placed it 5.7-8.1 ppm (4.9-7.0 kHz) above the bridge (`test-bench.md:418,452,522,622,658,721,759`). The warning's "from us" follows this sign.

**Threshold derivation.**

| Quantity | Value | Source |
| :--- | :--- | :--- |
| Channel filter bandwidth (`MDMCFG4 = AA`) | 135.4 kHz | `datasheets/cc110l.txt:3755-3763`, `_Static_assert` in `src/radio_bringup.c:139` [D] |
| Deviation (`DEVIATN = 40`) | 25.39 kHz | `cc110l.txt:3882-3906` [D] |
| Data rate | 49.99 kBaud | `cc110l.txt:3768-3778` [D] |
| Signal bandwidth (Carson: 2 × deviation + data rate) | 100.8 kHz | [I] |
| Datasheet rule: the signal should fill at most 80 % of the filter, with the crystal uncertainty subtracted | 0.8 × 135.4 - 100.8 = 7.5 kHz in total, ±3.8 kHz | rule `cc110l.txt:1645-1655` [D], numbers [I] |
| The signal's Carson bandwidth reaches the filter edge | (135.4 - 100.8) / 2 = ±17.3 kHz | [I] |
| FOC saturation, `FOCCFG = 16`: `FOC_LIMIT = 10` | ±BW/4 = ±33.9 kHz | `cc110l.txt:4045-4051` [D] |
| `FREQEST` resolution and range | 1586.9 Hz, ±202 kHz | `cc110l.txt:4429-4434` [D] |
| Crystal tolerance, each side | ±40 ppm (±34.7 kHz at 866.3 MHz) | `cc110l.txt:807-811` [D] |
| Bench: stock senders on channel 26 | 0 to -6 units (down to -9.5 kHz) | "P2 receive-only implementation (#9)" above [V] |
| Bench: our network on channel 16 | +1 to +3 units (up to +4.8 kHz) | below [V] |

The 80 % rule is already broken on the bench without any loss: 99.75 % CRC OK on channel 26 with senders at up to -6 units, and the ACKs on channel 16. So the rule marks best sensitivity, not the point where the link fails [I]. The datasheet says that offset compensation allows a narrower filter (`cc110l.txt:1653-1655,1679-1681`). That suggests the compensation re-centres the signal ahead of the channel filter, but the datasheet does not say so [I]. Without re-centring, the signal starts to leave the filter at ±17.3 kHz. With it, the loop saturates at ±33.9 kHz. 15 kHz (9.45 units, 17.3 ppm at 866.3242 MHz) sits below the more conservative 17.3 kHz, so the warning comes before either point. It is also 5.5 kHz (3.5 units) above the worst value seen on the bench, so the bench should not trigger it. Two crystals that are each within ±40 ppm can be up to 80 ppm (69 kHz) apart, so the warning can also fire for parts that are within the datasheet tolerance. That is intended: it is an early warning.

`FREQOFF_MIN_FRAMES = 4`: frame to frame, one device's `FREQEST` stays within one unit [V] (below), so 4 frames fix the mean to within a fraction of a unit; with fewer frames a single odd sample could decide.

**Bench data behind it [V].** The RTT logs of 12 runs on channel 16 (2026-11-17 to 2026-11-20; `~/ib01-captures/`, not in git), filtered on the results that `link_rx_from_network()` accepts: 704 frames, all +1 to +3 units, run means +1.72 to +3.00 units (+2.7 to +4.8 kHz), min..max within one run at most 1 unit apart. In five of these runs the minutes that had such frames had 1 to 18 of them, mostly 2 to 6.

**Conflict, not explained [I].** On channel 26 (2026-11-12) the stock senders read 0 to -6 units, and the coordinator's wake trains about -4.8. Yet the SDR places the coordinator within about 1 ppm of the bridge's carrier (measured from 2026-11-17 on) and the devices 1-8 kHz above it (`test-bench.md`, "Stock network reference"; open question 7). On channel 16 the spare device reads about 1.5 units below the difference the SDR measured. The bridge's own crystal on 2026-11-12 was not measured, and `FREQEST` may depend on the frame content. For this reason `FREQEST` is used here to watch for drift, with a wide margin, and not as an absolute measurement of the crystal.

**On the bench.** Expect `our network N frames, mean` between about +2.5 and +5 kHz and no warning line. The warning code path is covered by the host test only. A bench check would need a trimmed `FSCTRL0`, which is a test-only change and is not built in.

The trigger runs at a quiet moment of the radio task (no packet arriving, no coordinator transaction), never while a window is open: creating a network blocks the task for up to about 0.8 s (DRBG reseed, sector erases), so it cannot overlap a window or a transaction. The key and random bytes the trigger used are wiped right after the window opens (item 4).

"No network record at all" (`store_net_probe()`, `src/store.c:411`): neither slot starts with the record's magic. The magic is the commit mark, programmed last (`design.md`, "Slotted record, as built"), so a first write cut by a power failure leaves none, and a damaged or refused record (for example one for channel 26) keeps its magic: the bridge then refuses to create a network over it, because devices may still be paired to it. Host test: the probe after a cut at every step of a first write (`tests/host/test_store.c`).

**The window** (`src/pair.h`). **10 minutes** (`PAIR_WINDOW_MS`, owner spec 2026-11-17; 120 s before) from the button; from the server its duration, at most 10 minutes (#40); then it closes by itself. Closed earlier only by the button, by the server's duration 0, by a new key (`link_set_key()`) or by no key. A pairing does **not** close it: the target's 2.04 ends that exchange, and the same device may pair again while the window is open. While open it holds the pairing key's schedule and a copy of the network key; closing wipes both, so the key copy now lives up to 10 minutes in RAM (was at most 120 s, and until the 2.04). Per window, however many exchanges it holds, at most 16 beacons, 3 Router Advertisement pairs and 3 `d/pair` datagrams (each with the coordinator's 3 attempts): limits unchanged, see "Airtime". Only the target is answered: a Beacon Request from any other address is dropped before it is decrypted; a Data frame or broadcast that fails the network key is tried under the pairing key only if its source is the target (`src/link.c:163-231`). A window does not open while a frame of the last one is still queued (`csl_pairing_jobs()`, `src/csl.c:337`): a `d/pair` waiting for its retry, or an advertisement copy, would otherwise go out under the new window's pairing key with the old MID and session value, and its report would be taken for the new window's `d/pair` (fw-reviewer L3 of #19). After a close they go within seconds: those under the pairing key fail for want of it at their next attempt and are dropped without sending; the copy under the network key is sent. The button then logs `frames of the last window still queued` and opens nothing; the owner holds it again. Host test: `tests/host/test_link.c`, `test_pairing()`.

**Exchange.**
1. Window opens: the first Router Advertisement pair is due 1 s later, before any frame of the joiner, as on the commercial bridge (`freedo/docs/PROTOCOL.md:673-675`).
2. The target's Enhanced Beacon Request (27 bytes, sealed under the pairing key, MAC command `07`) gets an Enhanced Beacon (32 bytes) with the bridge's next seq and frame counter (`csl_take_seq_counter()`, `src/csl.c:350`, which also keeps a busy transaction from handing that counter out again), built while the request is taken (`on_beacon_request()`, `src/link.c:252`). Host test: freedo's request and beacon byte for byte (`tests/host/test_pair.c`, vectors from `freedo/tado/beacon_test.go:62,90`).
3. While the window has one of its 3 pairs left, every Router Advertisement goes twice: under the network key with Frame Pending (`59 e8`), then under the pairing key (`49 e8`), consecutive seq and counter, each behind its own 1 s train (`src/link.c:341`, `CSL_JOB_PENDING`; `freedo/docs/PROTOCOL.md:667-672`). The target's Router Solicitation under the pairing key asks for one (10 s hold-off between advertisements as before); once the pairs are used up it asks for nothing (see "Airtime" below).
4. `d/pair` goes `PAIR_DPAIR_DELAY_MS` (3 s) after the target's first pairing-key frame that is not a Beacon Request (its Router Solicitation comes 1.5-2.8 s after the beacon, `freedo/docs/PROTOCOL.md:664-665`), so that the advertisement pair it asked for goes first; 12 s after the first beacon if nothing else comes. It is a Data frame under the pairing key from UDP 5683 to 5683: `40 02 mid | b1 'd' | 04 'pair' | 11 2a | e8 06 e7 session(8) | ff 12 10 key(16)`, 43 bytes, MID from `0x4000-0x5FFF` (below the server's `0x7000-0xFFFF`, `tanoclo/ws-server/lib/coap-transport.js:39-44`), a new 8-byte session value per datagram from the DRBG. Host test: freedo's bytes (`freedo/tado/build_resources_test.go:196-203`). If its attempts fail, the target's next pairing-key frame brings another, up to 3.
5. The target's 2.04 ACK to that MID under the network key ends the exchange and is not relayed to the server (`src/link.c:197-201`); from then on its frames go to the server as any device's. The window stays open: a new Beacon Request of the target starts a new exchange with the same network key, while the window's limits last.

**Exchanges and the pairing LED** (owner spec 2026-11-17; `src/pair.c`, `src/radio.c`, `src/radio_pair.c`). An exchange starts when a beacon to the target is on the air (`pair_beacon_sent()`, from `link_beacon_done()`) or when a frame of the target under the pairing key arrives (`pair_note_joiner()`), and ends on the 2.04 to one of its own `d/pair` datagrams (paired), on any other answer to one of them or when the window's last `d/pair` failed (failed), or after `PAIR_EXCHANGE_IDLE_MS` = 30 s without progress (a beacon sent, a frame of the target, a `d/pair` queued; the time of a `d/pair` in flight does not count). A `d/pair` is due only during an exchange; its 12 s fallback is armed by a beacon that went out, no longer by a request that was only checked (before: armed even when the beacon was not sent). A 2.04 counts once per exchange, also when it comes late; a late answer to an earlier exchange's `d/pair` does not end the current one. The Router Advertisement pairs: the window's first advertisement, 1 s after it opens, and every advertisement during an exchange go as pairs while the window has one left; between exchanges the periodic ones (every 200-600 s, `src/link.c`) go as outside a window, under the network key alone and only if a network device was heard (`pair_ra_pair_wanted()`), so that a 10-minute window does not spend its 3 pairs before the target comes. PB8 (owner spec 2026-11-17, amended 2026-11-18; built, host-tested, flashed; the owner saw the pattern on the bench on 2026-11-18 and it is fine **[V, owner by eye]**, `test-bench.md`, "Factory reset and LEDs, owner check"; the pure phase function `pair_led_level()` in `src/pair_led.c`, `tests/host/test_pair_led.c`): off without a window; **slow flash** (500 ms on, 500 ms off) while the window is open and no exchange goes on; **quick flash** (100 ms on, 100 ms off) during an exchange; **fully on for 2 s** when a pairing succeeded (the paired counter of `pair_stats()` changed); then back to the slow flash while the window is open, off when it is over; a failed exchange goes straight back to the slow flash. Decisions the spec left open **[I]**: the 2 s hold runs to its end when the window closes during it (then off) and when a second exchange starts during it (then the quick flash follows); a second success inside the hold restarts the 2 s. The phases follow the tick clock; the radio task's loop waits at most 100 ms, so while an exchange is engaged the wait is capped to 20 ms (`src/radio.c`) to keep the 100 ms halves even; the slow flash and the hold are at most 100 ms late. No log line, lock or wait was added; the beacon scope marker below is unchanged. RTT: `pair: target found: pairing (LED lit)`, `pair: exchange over, window still open (LED flashing); exchanges N: paired N, failed N, no progress N`, `pair: window closed; ...`, logged at the next quiet moment of the radio task. Host tests: `tests/host/test_pair.c`, `test_exchange()`; `tests/host/test_link.c`, `test_pairing()`.

**Key exposure.** The network key crosses the air under the public pairing key (`radio.md`, "Exposure"). In RAM it is held, besides the link's AES schedule, only while needed: the window's copy (wiped on close), the `d/pair` job body and the frame sealed from it (wiped when the job ends or the pool is reset, `src/csl.c`), the driver's frame copy (wiped once the frame has left the chip or was abandoned, `tx_wipe()`, `src/cc110l.c:709`), and the builder's stack buffers (wiped after queuing). A `d/pair` already on the air when the window closes is not recalled: its transaction ends normally, at most about 1 s later.

**Transmit gate, rule 7 (#43, 2026-11-23):** `TXGATE_BAD_PAN`: wake-up frames and Enhanced Beacons must carry our network's PAN, set from the network record by `cc110l_set_pan()` (`src/network.c:69`, `src/txgate.c:170,251`); without a network nothing of the two goes out. Data, ACK and broadcast-data frames have no PAN field. The PAN is `0xABCD` in practice (`pan43-results.md`).

**Transmit gate.** The beacon rule compared all 8 bytes of our address at offset 13, but a beacon is sealed from byte 16 on (`freedo/tado/beacon.go:17-23`), so every real beacon was refused. It now checks the 3 clear bytes, PAN `cd ab`, that the answered request went to `ff ff` / `ff ff`, that the beacon's destination is the requester and not us, the pairing flag and the test channel (`src/txgate.c`, `MAC_BEACON` case). The driver passes the request's header to the gate through `cc110l_tx_answer()` (`src/cc110l.c:798`); `cc110l_tx_start()` has none, so a beacon cannot go out on the frame path.

### Remote trigger (#40) [I]

Built and host-tested 2026-11-20. `fw-reviewer` verdict A (safe to flash) on the commits up to `47fd3a4`, with low findings; L1 and L2 (below, "Hand-over" and "Copies") fixed after, delta review pending. Not flashed yet. Owner decision 2026-11-17 (`open-questions.md`, row 28a). The request, its checks and its answers: `server-api.md`, "Remote pairing trigger". Here: how it reaches the radio task.

- **Same window, same guards.** The net task (`src/session.c`, `on_pair()`) only checks the request (`pair_remote_check()`, `src/pair_remote.c`: path and serial, POST, payload, and the two build guards: a target named and the transmitter built in). The window is opened by the radio task, which owns pairing, through `pairing_open()`, the code the button uses, with every gate of the table above in the same order; the only difference is the length passed to `link_pair_open()`: `min(dur, 600)` s instead of 600 s. A window that is open is left as it is (length, per-window limits, an exchange in progress), whoever opened it: re-opening would reset the per-window limits and could wipe a `d/pair` in flight. Duration 0 closes it with `link_pair_close()`, as the button does. Without a target in the build `pairing_open()` compiles to "no target", as before.
- **Hand-over.** One slot in `src/pair_remote.c`, four states (empty, posted, claimed, done) moved by compare-and-swap (LDREX/STREX), as `src/handoff.c` does for the update: no lock and no critical section, so the GDO interrupts and the Enhanced ACK are never masked. `radio_request_remote_pairing()` sets `NOTE_PAIR_REMOTE` to wake the loop. While a request is posted the loop holds the coordinator (`csl_hold()`, as for the button) and runs it at `flash_quiet()`, right after the button's own trigger, because a first window may create the network (flash erase and program). The outcome goes back through the slot; the net task polls it in `session_poll()` (at least every 50 ms), answers and logs. If the radio task has not claimed the request after 10 s (its loop does not run), the net task withdraws it, answers 5.03, and the radio task never acts on it; a claimed request always finishes (at most about 0.8 s, a network creation). One request at a time: another one that arrives meanwhile (a close while an open is in work) gets no ACK, so tanoclo sends it again after its retry interval and it is acted on once the slot is free; a 5.03 would have stopped tanoclo's resends and lost it (fw-reviewer L1 of #40; `server-api.md`, "Remote pairing trigger").
- **Copies.** `pair_remote_sort()` (`src/pair_remote.c`) takes a request that passed the checks as new, a copy of the one in work (no answer until it is done), a copy of one acted on in the last 247 s (its first answer again, nothing done again), or one that waits (above). A copy is recognised by Message ID, token and duration, as tanoclo resends the very frame; the Message ID alone could match a new request after a tanoclo restart, which starts its IDs at a random point (fw-reviewer L2 of #40).
- **Deadlines.** Nothing new runs in an interrupt or inside a frame's timing. The radio task does the remote request where it does the button's (no packet arriving, no transaction set up), so the Enhanced ACK (0-1 ms) and the beacon answer (2.4-7.4 ms) are as for #19: the ACK interrupt is untouched, and the beacon's `csl_quiet_for()` gate holds whenever the coordinator is idle. A network creation blocks the radio task for up to about 0.8 s, as from the button (fw-reviewer items 1-3 of #19).
- **Stack.** By `-fstack-usage` (no LTO, 2026-11-20): the button and the server's request now both open through `pairing_open()` (80 B, not inlined), under `radio_task_run` (136 B, `pairing_trigger()` and `pairing_remote()` inlined), then `network_create()` and the DRBG as above: 216 B against 176 B before #40 measured the same way, so about 40 B more on the deepest path. The net task: `on_message` 312 B with `on_pair()` inlined (304 B before the request key of L2), `pair_log()` 248 B; within its 6 KB.
- **Host tests:** `tests/host/test_pair_remote.c` (276 checks): tanoclo's own request bytes for durations 300, 0 and 65535 and its ACK, eight paths that are not the pair path, eight other serials, the methods, eleven malformed payloads and well-formed variants (unknown tags, tag order, upper bytes set), the build guards, the codes, the request key (Message ID, token and its length, duration, open against close), the duplicate cache (lifetime across the clock's wrap, open-close-late open, a reused Message ID with another token or duration acted on and replacing the old entry, eviction), the sort (a close while an open is in work waits without an answer and is acted on at its resend once the open is done) and every move of the hand-over slot, including withdraw against claim. `test_pair.c` (176 checks, 156 before): the window's length (0 refused, 1 ms, 300 s, capped at 10 minutes, time left across the wrap).
- **Measure on the bench:** `test-bench.md`, "Remote pairing trigger (#40), plan". The beacon's timing marker is unchanged: PB8 (pairing LED) goes off while the beacon waits and on right after its STX strobe, so a scope on PB8 against GDO0 shows the request's end to STX, expected 3.7-3.9 ms as in the #19 run.

### Joiner report (#41) [I]

- **Radio task:** on `PAIRED` (the target's 2.04, `src/link.c`, `on_data()`), the link posts the joiner's address, the one its uplinks carry (`fe80::` + its interface identifier, from the 2.04's own source), into a queue of 4 (`pair_found_post()`, `src/pair_found.c`). Without a session it waits in the queue; RAM only, so a restart loses it (then register the device by hand).

Margins: 1.5 ms after the earliest and 3.4 ms before the latest start the device accepts; the commercial bridge listens 3.968 ms before its beacon (`freedo/firmware/cc1101_bridge/cc1101_bridge.ino:228-230`). A beacon not sent (end not seen live, busy, late, refused) costs one request: the device asks again 8 s later (`freedo/docs/PROTOCOL.md:662`). Nothing is logged before the beacon is on the air; then `pair: beacon seq NN to the target sent: STX N us after the request ended`. The minute log counts beacons sent and not sent by reason.

Effect on listen before transmit: none. The beacon is over within about 7.3 ms of the decision to send it (0.15 ms to STX, 75 µs, 43 bytes on air), so the 15 ms gate keeps it, and the log line after it, clear of the coordinator's next 3.968 ms listen; before the #19 review the gate was `csl_busy()`, which allows a listen 10 ms away, so a beacon could overlap and shorten it. The coordinator sets up no new transaction while the beacon is prepared and sent (only `csl_step()` does, in the same task), so an idle coordinator counts as quiet. Host test: `test_quiet_for()` in `tests/host/test_csl.c`.

Effect on the Enhanced ACK (#18): none on its path. The spin checks for a sync edge every 100 µs and gives up at once, so a Data frame arriving meanwhile is pumped and its ACK prepared as before; during the beacon itself the radio is in TX.

**Measuring it.**
1. SDR, primary (`rf-bench`): `tools/sdr/demod.py --channels 16 --summary` (`rtl_sdr -f 865924158`) reports the request-to-beacon gap (`test-bench.md`, "Demodulator"); expect 3.8-4.1 ms, accept 2.4-7.4 ms. With `hopcap.py`, nothing on channel 26.
2. RTT: the `pair: beacon ... STX N us` line; expect about 3.8 ms. It uses the bridge's own clock and the GDO0 stamp, so it misses the interrupt latency and the 75 µs to the air.
3. Scope, fallback: PB8 (pairing LED) is driven low when the beacon is ready, well before its moment (`beacon_answer()`), and **rises** right after the beacon's STX strobe (`send_frame()`), whatever the LED's flash phase or exchange state was; the low stretch is about 3.3 ms, too short to see. Before the owner spec of 2026-11-17 it fell at the strobe instead. A second probe on GDO0 (CC110L pin, MCU PA0): it falls at the end of the request and, in TX, rises when the beacon's sync word has gone out (`IOCFG0 = 06`). Gap request end to STX = PB8 rise minus GDO0 fall; preamble start = PB8 rise + 75 µs; cross-check: the beacon's GDO0 rise comes 75 µs + 8 bytes x 160 µs = about 1.36 ms after PB8 rises. Trigger on the PB8 rising edge; between beacons PB8 also toggles every 0.5 s (flashing), which the GDO0 fall about 3.9 ms before the edge tells apart.

**Airtime** **[I]**, charged as the driver does, (11 + length) × 161 µs + 100 µs per frame. Worst case of one window, every limit reached:

| What | Count | Each | Total |
| :--- | --: | :--- | --: |
| Enhanced Beacon (32 bytes) | 16 | 7.0 ms | 0.11 s |
| Router Advertisement pair: two 1 s trains of 12-byte wake-up frames, each followed by a 108-byte broadcast | 3 | about 2.04 s | 6.1 s |
| `d/pair` attempt without an anchor: 1 s train and the Data frame | 3 datagrams × 3 attempts | about 1.02 s | 9.2 s |
| **Window** | | | **about 15.4 s** |

That is half the 30 s per hour budget (`src/airtime.h`). The limits stay as reviewed for the 10-minute window (owner spec 2026-11-17): they are per window, however many exchanges it holds, so the worst case of one window is unchanged; a typical pairing uses one beacon, one pair and one `d/pair` [I], so a window holds up to three pairings; 16 beacons are far more than a joiner that takes the first one needs (one request every 8 s per channel it scans, `freedo/docs/PROTOCOL.md:662-663`, up to 75 on our channel in 10 minutes if none is taken). Per hour, at most six windows back to back could ask for 6 × 15.4 s; before, thirty 120 s windows could ask for more; in both cases the driver's 30 s budget is the bound. Nothing else is sent because of the window; the periodic advertisements between exchanges are the ones a bridge sends without a window. While it has a pair left, every advertisement goes as a pair or waits until both copies fit the queue, never as a lone copy (`router_advertisement()`, `src/link.c:341`). A second window in the same hour can run into the budget; the driver refuses what does not fit and counts it in the minute log (`tx_duty`).
